Boot sequence and profiles

From Limine handoff to PID 1. Boot is modelled as typed phases with preconditions; the idle loop starts once userspace is ready.

Phases

EarlyBootLimine responses, build identity
MemoryReadyphysical map, paging, heap
ProtectionReadyCPU protections (NX, SMEP/SMAP, KPTI)
InterruptsReadyGDT/IDT/TSS, ACPI, APIC
DevicesReadydriver probe, PCI
StorageReadyblock + filesystems
UserspaceReadyscheduler, PID 1, idle

Phase names come from PhaseId in kernel/src/boot_phase.rs; each transition declares its preconditions.

What happens

  1. Validate Limine responses and the build identity (commit + tree) injected by the binary crate.
  2. Bring up physical memory, paging and the heap; enable CPU protections.
  3. Install interrupt tables and architectural state for the BSP.
  4. Discover ACPI/APIC and pick a CPU policy.
  5. Initialise drivers and storage.
  6. Start the scheduler and launch PID 1, publish runtime state, enter idle.

Not every transition is independently qualified: boot::run and several init paths remain monolithic, and the driver registry is not the single probe authority.

CPU profiles

ProfileBehaviour
ContainedSingleCpu (default)Only the boot CPU schedules work.
r13-smp-probe featureExperimental: wakes APs for bounded timer / IPI proofs.
r13-smp-sched-probeAlso runs one pinned kernel task per AP. Never in product builds.

Profile policy lives in kernel-core::boot_profile so it is unit-tested on the host.
